# AsphaltCrash – Network Protocol

Protocol version: **1** (`v: 1` in every message).
Transport: WebRTC data channels via PeerJS 1.5.5 (see `ARCHITECTURE.md` section 6.7). Each remote peer uses two `DataConnection` objects: one with `reliable: true`, one with `reliable: false`.

---

## 1. Principles
1. Host is authoritative. Clients send intent (inputs), never state.
2. Two channels per connection: reliable/ordered for control and events, unreliable/unordered for high-rate state.
3. Every high-rate message carries a monotonically increasing `seq` or `tick` so stale data is discarded.
4. Inbound data is untrusted: validate every field before use (`validate.ts`). Invalid messages are dropped and counted; three invalid messages in 5 s disconnect the peer.
5. Encoding in v1 is JSON with short keys and numeric arrays. Binary (DataView) encoding is a planned v2 optimization, gated on measured bandwidth.

---

## 2. Identifiers
| Name | Type | Rule |
|------|------|------|
| `roomCode` | string, 6 chars | Alphabet `ABCDEFGHJKMNPQRSTUVWXYZ23456789` (31 chars, no `0 O 1 I L`; unbiased sampling rejects bytes ≥ 248). |
| `hostPeerId` | string | `asph-` + `roomCode`. |
| `playerId` | integer 0–15 | Assigned by host. Slot index (0..`maxCars`-1). Human and bot share the same range. |
| `playerToken` | string, 16 chars | Random, generated by client, sent in `hello`. Used for reconnect. |
| `matchId` | integer | Host increments per match. |
| `seq` | integer | Per-sender, per-channel, wraps at 2^31. |
| `tick` | integer | Host simulation step counter since match start. |

## 3. Connection lifecycle

```
Client                                             Host
 │  open PeerJS connection to asph-<code>          │
 │ ─────────────── hello{v,name,token} ───────────►│  check version, room state, slot count
 │                                                 │  if room full or match running → reject
 │ ◄────────────── welcome{playerId,lobby} ─────── │  or reject{reason}
 │ ◄────────────── lobby{...} (on each change) ─── │
 │  (lobby phase)                                  │
 │ ◄────────────── start{matchId,seed,config,...}  │
 │ ─────────────── ready{matchId} ────────────────►│  client has loaded arena
 │ ◄──────────────── snap / ev (match running) ──── │
 │ ─────────────── in (input, 30 Hz) ────────────►│
 │ ◄──────────────── end{scores} ────────────────── │
```

Clients must send `ready` before the host includes them in the simulation tick for that match. Before `ready`, the car is spawned but frozen.

## 4. Message catalogue (v1)

Field names are short to reduce bytes. Documented mapping is normative.

### 4.1 Control (reliable)

| `t` | Direction | Fields | Notes |
|-----|-----------|--------|-------|
| `hello` | C→H | `v` (int), `name` (string ≤ 16 chars), `token` (string 16) | First message after open. |
| `welcome` | H→C | `pid` (int), `lobby` (LobbyState) | Accepted. |
| `reject` | H→C | `reason`: `version` \| `full` \| `running` \| `invalid` | Host closes connection afterwards. |
| `lobby` | H→C | `players`: `[pid, name, kind, ready]`, `bots`: int, `cfg`: partial config | Broadcast on change. `kind` = `h` (human) or `b` (bot). |
| `cfg` | H→C | `cfg`: MatchConfig subset | Included in `lobby`. Separate type reserved for v2. |
| `start` | H→C | `mid` (matchId), `seed` (uint32), `cfg` (MatchConfig), `spawns`: `[pid, x, y, angle][]`, `bills`: none (generated from seed) | Match begins after all `ready`s or 5 s timeout. |
| `ready` | C→H | `mid` | Client loaded arena. |
| `pause` | H→C | `on`: bool, `why`: `host` \| `player` | Host paused (host hidden) or a player paused. |
| `ev` | H→C | `k` (event kind), `d` (payload) | See 4.3. Reliable. |
| `end` | H→C | `mid`, `scores`: `[pid, cash, kills, delivered][]`, `winners`: `pid[]` | Match finished. |
| `bye` | both | `why` | Graceful leave. |
| `ping` | C→H | `c` (client ms) | Every 2 s. |
| `pong` | H→C | `c` (echoed), `h` (host ms) | Used for RTT and offset. |
| `resume` | C→H | `v`, `token`, `mid` | Reconnect attempt. Accepted if `pid` slot reserved and within window. |
| `resumeOk` | H→C | `pid`, `tick` | Host returns current tick. Client requests fresh state via next snapshot. |

### 4.2 High-rate (unreliable)

| `t` | Direction | Rate | Fields |
|-----|-----------|------|--------|
| `in` | C→H | 30 Hz, plus on button edge | `s` (seq), `ax` (aim X, int −100..100), `ay` (aim Y, int −100..100), `a` (action bool, 0/1) |
| `snap` | H→C | 20 Hz (every 3rd tick at 60 Hz) | `k` (tick), `ak` (ackSeq of the receiving player's last applied input, 0 for bots/none), `cars`, `bills`, `tm` (match time remaining, ms) |

#### 4.2.1 `snap.cars` item
`[pid, x, y, a, vx, vy, hp, flags, cargo, score]`

| Idx | Name | Type | Encoding |
|-----|------|------|----------|
| 0 | pid | int 0–15 | raw |
| 1 | x | number | round to 0.1 px |
| 2 | y | number | round to 0.1 px |
| 3 | a (heading) | int | rad × 1000, range −3142..3142 |
| 4 | vx | int | px/s rounded |
| 5 | vy | int | px/s rounded |
| 6 | hp | int 0–100 | raw |
| 7 | flags | int bitmask | bit0 = destroyed, bit1 = respawning, bit2 = boosting, bit3 = braking, bit4 = carrying |
| 8 | cargo | int 0–cap | number of bills carried |
| 9 | score | int | cash total |

#### 4.2.2 `snap.bills` item
`[id, x, y, v]` where `id` is int, `x,y` rounded to 1 px, `v` is value (10, 20 or 50). Only bills that are on the field, not carried, are sent. Carried bills are represented by `cargo` count.

Bills are sent in full every snapshot in v1 (max 12 items). Delta is not needed at this size.

#### 4.2.3 Size estimate
- Car item: about 40 bytes JSON.
- 8 cars: about 320 bytes. 12 bills: about 120 bytes. Envelope about 40 bytes.
- Total about 480 bytes per snapshot, 20 Hz → about 9.6 KB/s per client worst case (8 cars). Typical 4 cars: about 5 KB/s.
- Input: about 40 bytes at 30 Hz → about 1.2 KB/s per client.

This is within budget. If measured worse than 20 KB/s, switch to binary (v2).

### 4.3 Events (reliable, `ev`)

| `k` | `d` payload | Meaning |
|-----|-------------|---------|
| `pick` | `[pid, billId, value]` | Bill picked up. |
| `drop` | `[pid, count]` | Cargo dropped (car destroyed). Bills respawn as field bills (ids new). |
| `deliv` | `[pid, amount]` | Cargo delivered to home base. |
| `hit` | `[attackerPid, victimPid, impulse]` | Significant collision (impulse above `hitEventThreshold`). Used for sparks and HUD feed. |
| `kill` | `[attackerPid, victimPid]` | Car destroyed by collision. |
| `respawn` | `[pid, x, y, a]` | Car respawned. |
| `billNew` | `[id, x, y, v]` | New bill spawned (also in snapshot, event is for sound). |
| `timer` | `[remainingMs]` | Only at 30 s, 10 s, 0 s. |

Events are reliable and ordered. Clients must apply events in order. Duplicate events (same host `tick` and `k` and payload) are ignored.

## 5. Input semantics
- `ax`, `ay` = aim vector in screen space (+x right, +y down), each int −100..100 (scaled to −1..1 on the host). The vector is the joystick direction, not relative to the car. The host turns the car toward the aim and drives once aligned (`src/game/sim/aimDrive.ts`).
- `a` = action button (boost/handbrake).
- Host stores latest input per player and marks `seq`. It applies the input on each tick until a newer one arrives (zero-order hold). If no input arrives for 500 ms, the car's input is set to neutral (aim 0,0, no action). This protects against dropped unreliable packets.
- Clients send the latest `seq` even when the joystick is at rest. Idle heartbeats at 10 Hz keep `ackSeq` moving.

---

## 6. Clock and interpolation
- `ping` every 2 s. `pong` contains host time `h`.
- `hostTimeOffset = h - (c + rtt/2)` where `rtt = now - c`. Median of last 5 samples.
- Client render time `renderTime = hostNow - INTERP_DELAY_MS` with `INTERP_DELAY_MS = 100`.
- Snapshots carry `k` (tick). Host tick maps to host time as `k * STEP_MS`. Clients use this mapping with the offset to sample the buffer.

## 7. Validation rules (inbound)

| Message | Rule |
|---------|------|
| all | `v` must equal 1 for `hello`/`resume`; other messages from connected peers must be JSON object with `t` string. |
| `hello` | `name` string, trimmed, 1–16 chars, printable. `token` 16 chars `[A-Za-z0-9]`. |
| `in` | `s` int ≥ 0 and greater than last accepted seq (older ones dropped). `ax`, `ay` int in −100..100 (out-of-range message dropped). `a` 0 or 1. |
| `ready` | `mid` equals current match id. |
| `resume` | `token` must match stored token for slot; window not expired. |
| `ping` | `c` finite number. |

Any violation: drop the message and increment `invalid` counter for that peer. Three invalid messages within 5 s → disconnect with `reject{reason:'invalid'}` and `bye`.

---

## 8. Reconnection
1. Client loses connection (not `bye`). It stores `{roomCode, token, mid, pid}` in `sessionStorage`.
2. Client reopens PeerJS connection to `asph-<code>` and sends `resume`.
3. Host checks `token` against slot `pid`, and that `now - disconnectedAt < 45 s`.
4. Host sends `resumeOk`. Slot becomes human again. Next snapshot carries current state.
5. If window expires: host releases slot. Car becomes a bot until match end.

Host disconnect: clients receive connection close. Client shows "Host disconnected" and returns to start screen. `sessionStorage` entry is cleared.

Host paused (tab hidden on host): host sends `pause{on:true,why:'host'}` only if it can (page is still running in background, which is rare on iPadOS). If the host page is fully suspended, clients detect silence: no `snap` for 3 s → show "Host unresponsive" overlay. If no snapshot for 15 s → treat as host loss.

---

## 9. Versioning
- `v` in every `hello`/`resume`. Host rejects mismatch with `reason: 'version'`.
- Additional optional fields may be added in v1 without bumping `v`; clients ignore unknown fields. Removed or renamed fields require bump to `v: 2`.
- Unknown `t` values are dropped and logged in debug mode, not treated as fatal.
